## 1. 开发目标

实现一个面向柬埔寨招聘市场的 Telegram 原生匹配服务。第一版的核心承诺是：

- 企业和求职者完全免费；
- 根据技能、行业、岗位、工作内容匹配；明确的必须条件冲突直接不展示；
- AI 只负责整理草稿，必须由本人检查、修改、确认；
- 企业官网岗位可被采集并推荐；企业未入驻时只跳转官网申请；
- 入驻企业和求职者对同一岗位互相感兴趣后，立即开放联系方式；
- 收到站内兴趣后 24 小时提醒，超过 72 小时未处理暂停相关推荐；
- 招满或找到工作后可以立即退出推荐。

当前仓库只有产品设计文档，没有现成 Bot、爬虫、数据库或运行服务。请先实现可运行的最小闭环，再扩展功能。

## 3. 建议开发顺序

### 阶段一：基础 Bot 与数据层

实现 Telegram `/start`、语言/角色选择、会话恢复、求职者资料、企业资料、岗位草稿和基本菜单。

要求：

- 使用服务端会话状态，不依赖客户端按钮参数决定权限；
- 每个按钮绑定对象 ID 和版本号；
- 草稿与已确认版本分开保存；
- 一个 Telegram 账号可以同时有求职和招聘角色；
- 所有操作保留服务端时间和审计事件。

### 阶段二：AI 整理与本人确认

输入可以是自然语言、粘贴简历或粘贴招聘说明。流程固定为：

`输入 → AI 提取字段 → 只追问关键缺项 → 预览 → 用户修改/确认 → 发布`

AI 不得：

- 虚构技能、经验、证书、工资、语言或工作许可；
- 把“优先”改成“必须”；
- 代替用户发布、表达兴趣或开放联系方式；
- 用未确认内容覆盖用户已经确认的字段。

AI 不可用时必须能手动完成。模型输入视为不可信数据，不能执行岗位文本中的指令。

### 阶段三：官网岗位采集

先支持人工配置的官网来源清单，再实现每日采集。每个来源至少保存：企业名称、招聘页 URL、访问方式、最近成功检查时间、状态。

每个岗位保存：

- 官方岗位名称和岗位 ID（有则保存）；
- 原始链接；
- 原始发布日期和截止日期（没有则为空）；
- 结构化的行业、岗位、技能、工作内容、地点、语言、班次；
- 首次发现时间、最近成功检查时间；
- `external`（官网采集未入驻）、`claimed`（企业认领）、`closed` 状态。

采集规则：

- 优先使用官网公开接口、订阅或稳定页面；遵守站点限制，不绕过登录、验证码或访问控制；
- 访问失败或解析异常进入 `needs_review`，不能直接判定岗位已招满；
- 同一官方岗位重复采集不能重复创建；条件变化要生成版本；
- 官网未公开薪资时，卡片显示“薪酬：面议”，并注明“官网未公开薪资”；不得估算金额；
- 官网岗位必须显示原始来源和最后成功核查时间。

官网未入驻岗位只能提供“查看原文”和“前往官网申请”，不能产生企业兴趣、站内 Match 或 24/72 小时处理计时。

### 阶段四：匹配与兴趣

匹配主干字段：技能、行业、岗位、工作内容。地点、语言、班次、到岗时间和工资只有在企业明确要求或用户明确设为“必须”时才作为硬过滤条件。

规则：

- 明确硬冲突：不展示；
- 硬条件缺失：进入待补充，不标为“符合”；
- 官网薪资未公开：作为特殊展示例外，显示“面议”，不因薪资未知隐藏；
- 非必须字段未知：可以展示，写明“未提供”；
- 同义词可以归一化，否定句不能误判为具备技能；
- 不生成没有依据的精确匹配百分比。

匹配唯一键：`candidate_id + job_id`。

入驻路径状态：

`candidate/job active → interest pending → accepted/declined → match`

同一岗位的双方有效兴趣产生一个唯一 Match。发送兴趣前必须告诉用户：对方也感兴趣后，会立即看到双方选定的联系方式。双方兴趣成立后立即开放联系，不再增加第二轮联系方式授权步骤。

## 4. 24/72 小时处理规则

计时只针对入驻企业与求职者之间的站内待处理兴趣。

| 时间 | 行为 |
|---|---|
| 通知成功且待办可见 | 记录 `notified_at`，开始计时 |
| 24 小时未接受/拒绝 | 发送一次提醒，记录 `reminded_at` |
| 超过 72 小时未处理 | 求职者暂停求职推荐；企业暂停该岗位的新推荐和新兴趣接收 |
| 接受或拒绝 | 视为已处理，停止该条计时 |
| 恢复 | 处理超时待办并确认仍在招聘/求职后恢复 |

登录、点击“稍后”、普通已读不算处理。通知失败或送达不明不能处罚用户。官网申请和 Match 后的私人聊天不计入此规则。

## 5. 最小数据模型

建议使用关系数据库；字段名称可调整，但以下事实必须保留：

| 表 | 核心字段 |
|---|---|
| `users` | `id`, `telegram_user_id`, `username`, `language`, `status` |
| `candidate_profiles` | `user_id`, `skills`, `industries`, `roles`, `task_keywords`, `hard_conditions`, `version`, `confirmed_at`, `status` |
| `companies` | `id`, `name`, `website`, `verification_status`, `verified_at` |
| `jobs` | `id`, `company_id`, `source_type`, `source_url`, `source_job_id`, `title`, `industry`, `skills`, `tasks`, `salary_status`, `salary_text`, `version`, `status`, `last_checked_at` |
| `interests` | `candidate_id`, `job_id`, `actor_side`, `job_version`, `candidate_version`, `status`, `notified_at`, `reminded_at`, `processed_at` |
| `matches` | `candidate_id`, `job_id`, `version`, `created_at`, `contact_opened_at`, `status` |
| `contact_methods` | `user_id`, `type`, `value_ref`, `share_enabled`, `verified_status` |
| `notifications` | `dedupe_key`, `recipient_id`, `type`, `status`, `attempts`, `last_error` |
| `crawl_runs` | `source_id`, `started_at`, `finished_at`, `status`, `new_count`, `changed_count`, `error_count` |
| `audit_events` | `actor_id`, `object_type`, `object_id`, `action`, `version`, `created_at` |

数据库必须对 `candidate_id + job_id + actor_side + version` 和 Match 组合设置唯一约束，防止重复兴趣和重复 Match。异步通知发送前重新检查删除、拉黑、关闭岗位和版本状态。

## 6. Bot 必须具备的入口

`/start`：开始或恢复  
`/menu`：首页  
`/profile`：查看/编辑求职卡或企业资料  
`/matches`：查看 Match 与联系方式  
`/settings`：语言、通知、可见范围、联系方式  
`/help`：规则说明  
`/cancel`：退出当前编辑并保留草稿  
`/delete`：确认删除资料

官网岗位卡片按钮：`查看原文`、`前往官网申请`、`跳过`、`信息有误或已失效`。  
入驻岗位卡片按钮：`感兴趣`、`跳过`、`举报/屏蔽`。  
收到兴趣按钮：`接受`、`不合适`、`稍后处理`。

## 7. P0 验收标准

1. 新用户可以从 `/start` 完成求职者建档，AI 失败时仍可手动完成。
2. AI 未确认的字段不会公开；用户修改后，迟到的 AI 结果不能覆盖。
3. 明确技能/职责硬冲突的岗位不展示；官网未公开薪资的岗位显示“面议”并照常展示。
4. 官网未入驻岗位只能跳转原站申请，不产生站内 Match 或 24/72 小时处罚。
5. 企业和求职者均不出现支付、会员、付费解锁或佣金页面。
6. 双方必须针对同一 `job_id` 表达兴趣；接受后只产生一个 Match。
7. 双向兴趣成立后立即开放双方预先选定的联系方式。
8. 24 小时提醒只发送一次；超过 72 小时暂停正确的求职者或岗位。
9. 招满、找到工作、暂停、删除、拉黑都能阻止新的推荐和联系释放。
10. 官网抓取失败不把岗位标为已招满；重复采集不生成重复岗位。
11. 所有关键动作可在审计记录中追溯，通知失败与用户未处理分开统计。

## 8. 明确暂不做

- 不做收费、广告、付费曝光、佣金和会员；
- 不做自动录用、自动面试安排或薪资谈判；
- 不把官网采集岗位伪装成企业已入驻；
- 不读取用户与企业在 Telegram 中的私人聊天；
- 不因官网没有薪资而隐藏岗位或虚构薪资；
- 不把“打开官网”计为已投递，不把“联系方式已开放”计为已聊天；
- 不先做全柬埔寨全品类的复杂排序，先保证单条岗位和单个城市/类别的闭环可验证。

## 9. 交付要求

Trae 完成每个阶段后，提交：

1. 可运行代码和启动说明；
2. 数据库迁移/初始化方式；
3. Telegram 测试账号操作路径；
4. P0 验收项的实际测试记录；
5. 未实现项、已知限制和需要人工配置的官网来源清单。

仅能启动 Bot、能回复 `/start` 或本地测试通过，不代表招聘闭环完成。必须至少用两个测试账号验证：建档、官网岗位跳转、入驻岗位双向兴趣、立即开放联系方式、24 小时提醒和 72 小时暂停。
