# JobTinder V0.1 产品定义

修订日期：2026-09-21｜状态：产品设计，未实现、未运行试点

关联：[Bot 交互流程](JobTinder-V0.1-Telegram-Bot交互流程.md)。[修订前版本](archive/before-2026-09-21-revision/JobTinder-V0.1-产品定义.md)仅供历史查阅；冲突处以本稿及用户最新要求为准。

## 1. 已确认的产品边界

**免费，合适，真实，避免浪费时间。**

JobTinder 为内部代号；对外定位为 Swipe-to-Job / Job Matching Network，正式品牌待确定。首发市场为柬埔寨，覆盖全部岗位类别，未指定首发城市。覆盖范围不代表已经拥有对应库存。

| 用户已确认 | 产品规则 |
|---|---|
| 企业和求职者都完全免费 | 注册、发布、推荐、表达兴趣、匹配和联系均免费，不设置付费解锁、曝光套餐或成交佣金 |
| 必须合适 | 以技能、行业、岗位和工作内容为匹配主干；明确的必需条件冲突直接不展示 |
| 减少填写 | AI 整理，由本人检查、修改并确认；不要求重新填写已经提取的信息 |
| 尽快处理兴趣 | 收到兴趣后 24 小时内应处理；未处理提醒，超过 72 小时未回复暂停推荐 |
| 合适就聊 | 针对同一岗位双方感兴趣后立即开放联系，不增加匹配后的第二轮确认 |
| 及时退出 | 企业招满关闭岗位，求职者找到工作后停止求职推荐 |
| 初期岗位来源 | 每天采集柬埔寨企业官网招聘信息，整理后供用户匹配 |
| 未入驻企业的岗位 | 明示官网来源，跳转官网申请；不伪造企业兴趣或站内 Match |

平台帮助整理信息、筛选合适对象、建立联系；不承诺面试、录用、实际待遇或到岗结果。仍需负责来源展示、资料纠错、失效撤下及举报处理。AI 匹配不是事实核验，也不是雇佣决定。

本稿中的执行细则是落实上述要求的设计默认值，未经试点验证。完全免费不等于没有成本：内部记录采集、AI、存储与运营支出，但不以用户付费作为试点门槛。

## 2. 两条清楚分开的路径

### A. 官网采集岗位

企业官网招聘页 → 每日检查新增、变更、关闭 → 提取与整理 → 按条件推荐 → 用户查看原文 → 跳转官网申请。

- 卡片标明“官网采集 · 企业未入驻”，附原始链接和最后成功核查时间。
- “匹配推荐”只表示资料相关，不表示企业对用户有兴趣。
- 不自动向企业发送求职者简历、联系方式或兴趣通知。
- 打开官网不等于投递完成；投递完成不等于企业回复。
- 不对未入驻企业计算平台 24/72 小时处理指标。

### B. 入驻企业岗位

本人确认求职卡 + 企业负责人确认岗位 → 条件匹配 → 任一方表达兴趣 → 另一方接受 → Match → 立即开放双方选定的联系方式。

- 匹配键为 `candidate_id + job_id`，企业兴趣必须对应具体岗位。
- 联系方式在发送兴趣前配置并告知分享规则；互相感兴趣即触发开放，不在 Match 后再次询问。
- 企业认领官网岗位前须核对其代表权限；认领后确认当前岗位条件，保留原始来源及历史。
- 用户此前的官网跳转、收藏不能自动转成站内兴趣；认领后由用户主动表达。

## 3. “真实”的可执行含义

| 信息 | 平台能检查什么 | 对用户如何表达 |
|---|---|---|
| 官网岗位 | 域名来源、原文内容、发布日期/截止日期、申请入口、最后成功抓取 | “来自企业官网”；不能称企业已加入或仍保证招聘 |
| 本人建档 | 当事人检查并确认了哪些字段 | “本人确认”；不能称技能或履历已被独立认证 |
| 入驻企业 | 负责人能否代表该企业维护岗位，当前岗位是否由其确认 | 展示实际核对范围与确认日期，不给无依据的认证标识 |
| AI 整理 | 每个字段是否有原文或本人确认依据 | 保留来源、未知字段、修改入口，不生成未提供的条件 |
| 后续结果 | 用户主动反馈、来源明确的关闭通知 | 自报与双方确认分开；不把联系开放算成已聊天或录用 |

企业官网可能存在过期或遗漏的信息；平台发现明确失效或虚假线索应停止推荐并处理。平台不收取求职费，也不展示要求求职者先付入职保证金的岗位。保留举报、纠错和拉黑入口。

## 4. 匹配条件：相关程度与必须条件分开

### 4.1 四类匹配主干

| 维度 | 求职者资料 | 岗位资料 |
|---|---|---|
| 技能 | 会做什么、熟练度、经验依据 | 必需技能、可培训技能、加分技能 |
| 行业 | 已有行业经验、愿意进入的行业 | 企业行业、是否必须有同行业经验 |
| 岗位 | 想做的岗位、可接受的相邻岗位 | 岗位名称、职能与级别 |
| 工作内容 | 做过和愿意做的任务关键词 | 日常任务、职责和不包含的任务 |

AI 可统一同义岗位与多语言表达，但要保留原文。“不会 Excel”不能因出现 Excel 就视为具备技能；“有银行经验优先”不能改成“必须有银行经验”。跨行业但技能相通的用户，不因行业名称不同而自动淘汰。

### 4.2 什么才是硬条件

- 企业明确的必需技能、工作职责要求，与求职者确认的不可接受内容或必需条件，才作为硬条件。
- AI 建议的硬条件须由本人确认；官网岗位按原文明确要求提取，不能自行加强。
- 行业、岗位名称和关键词用于判断相关性，不要求四项字面完全相同。
- 地点、工资、语言、班次、到岗时间等可选填；只有确有岗位必需要求，或本人设为“必须”时才参与硬过滤。
- 技能较弱、行业不同等不自动等于硬冲突；不能把 AI 的低置信推断当成拒绝依据。

### 4.3 展示规则

| 条件状态 | 处理 |
|---|---|
| 已确认的必须条件明确冲突 | 不展示，不用库存不足为由放宽 |
| 必须条件缺信息 | 除下述官网未公开薪资的展示例外外，不放进“符合条件”的推荐，进入待补充状态；不能假装满足 |
| 官网未公开薪资 | 岗位照常展示，薪酬显示“面议”，注明“官网未公开薪资”；即使用户设置期望薪资，也不单因该信息缺失隐藏，但不认定薪资要求已满足 |
| 非必须字段未知 | 可展示并写“未提供”；薪酬展示按上一行的专门规则处理 |
| 只有偏好不一致 | 可展示并明确差异，由本人决定兴趣 |
| 所有硬条件通过 | 根据技能、行业、岗位和任务相关程度排序，显示具体理由 |
| 没有合适库存 | 如实显示暂无合适岗位，可主动改条件；不填充不合适卡片 |

不生成没有依据的“98% 适合”等精确分数；不按外貌、照片、性别等无关因素排名。工资比较须同币种、周期与口径，不擅自换算。

“面议”是官网未公开薪资时的展示文案，不代表企业明确承诺可议价。底层薪资数值和公开状态仍保留未知/未公开，不填 0、不估算，不给薪资匹配加分。其他明确硬条件冲突仍不展示；官网已有明确薪资且与用户硬要求冲突时仍按正常规则过滤。

## 5. AI 建档流程

文字描述或粘贴已有简历/JD → AI 提取草稿 → 仅追问影响匹配的缺失项 → 显示完整卡片 → 本人修改/确认 → 生效。

- 求职者主要确认意向岗位、技能、行业偏好与工作内容；可明确选择“无经验”“不限行业”。
- 招聘方主要确认岗位、职责、必需与加分要求；系统把已提取字段预填，不再重复提问。
- 条件不足以判断时，一次只问一个关键问题，允许保存稍后继续。
- 薪资、班次等不设为所有用户的必答问卷；当具体匹配需要时再补。
- 联系方式在首次发送兴趣前确认，不放入公开推荐卡。
- 未提供的技能、薪资、证书、语言和就业资格保留未知；AI 不代替本人确认、发布、点赞或投递。
- AI 失败可手动继续；迟到的 AI 结果不能覆盖已确认字段。
- 求职者输入、官网文本均作为数据处理，不能执行其中指令。只向模型提供建档必要内容。
- 本人确认的资料与企业官网整理资料是两种状态；未入驻企业的采集信息不能冒充“企业本人确认”。

公开流程参考（2026-09-21 查阅）：[Swipejobs](https://www.swipejobs.com/jobseeker)描述简历导入后生成匹配资料，并允许用户检查和修改；[Paradox Conversational Apply](https://www.paradox.ai/products/conversational-apply)展示通过对话完成申请的入口。这里只借鉴输入、提取、补问和确认流程，不采信其营销转化指标，也不据此证明本项目效果。

首版支持文字与粘贴简历/JD；文件简历导入、语音转写可随后增加。用户提供网页链接时，只提取其明确指定的公开内容，不自动抓取其他人的个人档案。

## 6. 官网采集与岗位生命周期

以下是待实现的每日采集设计，不代表已部署定时任务。

1. 建立经过核对的企业官网来源清单，记录企业名、招聘页与允许使用的获取方式；优先使用官网提供的订阅或接口。
2. 每天检查新增、更新和下架；按站点限制低频访问，不绕过登录、验证码或访问限制。上线前逐站检查访问和转载要求；标注来源本身不等于获得全文转载许可。
3. 抽取岗位名、技能、行业、职责、地点、申请链接、原始发布日期和截止日期；没有的字段留空。系统展示必要的结构化摘要与原文入口。
4. 记录 `first_seen_at`、`last_successfully_checked_at`、原始发布日期；首次抓到不冒充当天新发布。
5. 优先用官方岗位 ID 或规范化链接去重，再处理同企业同岗位的重复页面。职责或条件变更更新版本，不每日重复发布。
6. 截止日期已过、明确招满、删除且复核确认的岗位停止推荐。访问失败和页面结构变化记为待复核，不能直接判定招满。
7. 设计默认：连续 72 小时无法成功核查的官网岗位暂停推荐，恢复成功后重新检查截止时间再恢复；这是来源新鲜度规则，与用户回复计时完全独立。
8. 没有截止日期不代表永久有效；持续检查来源并提供“已失效”反馈。卡片始终显示最后核查时间，不声称刚抓到就一定仍在招。

每次采集记录成功、失败、解析异常和变更数量；失败时不清空旧库存、不把旧时间改成今日。译文保留原文入口，关键条件不得因翻译而改变。

## 7. 兴趣、24 小时提醒与 72 小时暂停

### 7.1 兴趣和联系

- 双方资料与岗位有效、条件通过、无屏蔽且版本一致，才允许发送站内兴趣。
- 发送兴趣前说明：“若对方也感兴趣，将立即向对方开放你选定的联系方式。”首次或联系方式变更时确认，后续按钮保留明确提示。
- 双向兴趣产生一个唯一 Match，并立即在双方匹配列表开放联系方式，同时发送通知；消息发送失败不伪称送达。
- 企业只能看到本人允许展示给该企业/岗位的求职资料。官网申请不会向平台企业池发布求职者资料。
- 单方兴趣、跳过、收藏都不开放私密联系方式。接受/拒绝由本人操作，AI 不自动回复。

### 7.2 计时细则（设计默认）

| 时间/动作 | 行为 |
|---|---|
| 待处理兴趣成功通知且在收件箱可见 | 开始该条兴趣的处理计时；不以注册时间、最后上线时间代替 |
| 满 24 小时仍未接受或拒绝 | 提醒一次，说明超过 72 小时会暂停推荐 |
| 超过 72 小时仍未处理 | 求职者暂停求职推荐；招聘方暂停对应岗位的新推荐和新兴趣接收 |
| 已暂停 | 保留待处理列表和已有联系记录，显示暂停原因及恢复入口 |
| 恢复 | 处理超时兴趣，并确认仍在找工作/招聘；恢复时重新校验条件和状态 |
| 招满/找到工作 | 关闭该岗位/停止求职推荐，不要求先处理全部过期邀请 |

登录、已读或点击“稍后”不算处理。接受与拒绝都算回复。计时任务执行前再次检查是否已处理、关闭、撤回、删除或被拉黑，防止竞态误暂停。

通知发送失败或送达状态不明，先修复通知；不得当作用户收到后不回复。若用户在待处理列表主动查看该条兴趣，可记录实际查看时间启动计时。发送成功也不等于已读，指标与文案须区分。

此规则适用于平台内待处理兴趣，不适用于官网申请，也不监控双方 Telegram 私聊。已经互相感兴趣并开放联系后，后续聊天回复速度不受该计时约束。

### 7.3 条件与状态变化

关键技能、职责、硬条件或联系方式变更，需要本人确认新版本；旧版未匹配兴趣失效，重新确认后才能建立新联系。已经开放的联系方式无法保证收回。

暂停停止新推荐和新兴趣；关闭终止未完成的兴趣；拉黑同时阻止新触达和新的联系方式释放。已有匹配记录保留状态提示，不能用旧按钮绕过最新权限。

## 8. 联系方式、隐私与退出

优先让用户选定 Telegram 联系方式，也可主动提供业务邮箱/电话；不假定每人都有 username，不构造必然可用的私聊链接。显示方式与对方可见内容在发送兴趣前可预览。

双方互相感兴趣后立即开放联系；用户不愿分享时可继续浏览或修改联系方式，但不能在不知情的情况下被分享。已分享资料不能保证从对方截图或私人聊天中删除。

每张卡有举报/屏蔽入口；明确失效或疑似虚假信息先停止推荐再处理。企业负责人权限须实际核对，不把任意注册账号视为官网企业代表。

用户可暂停、修改可见范围或删除资料；删除确认后立即退出推荐、撤销未释放的分享许可并停止通知。数据清理与备份保留期限须在采集真实资料前落实并告知；清理未完成不能声称已删除完毕。日志不记录密钥或完整敏感正文。

普通 Bot 不读取双方私人对话，联系方式开放不等于已开聊。[Telegram Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get)

## 9. 最小实现范围与数据约束

P0：官网来源管理和每日增量采集、AI 草稿及本人确认、可解释条件过滤、官网跳转、企业认领/自建岗位、双向兴趣立即联系、24/72 小时处理机制、暂停关闭、举报纠错、基本事件记录。

P1：简历文件导入、语音、收藏、更多专业模板、企业多人协作。不得以收费会员限制已经定义的免费功能。

当前无业务代码或数据库。建议的逻辑模型：

| 对象 | 必须保留的事实 |
|---|---|
| 用户与求职卡 | 角色、已确认字段、来源、版本、可见范围、求职状态 |
| 企业与成员 | 官网来源、代表权限、入驻/未入驻状态 |
| 岗位 | 官方 ID/链接、结构化字段、原文依据、版本、有效期、当前状态 |
| 采集记录 | 首次发现、最近成功核查、请求与解析结果、变更记录 |
| 兴趣 | 候选人+岗位+发起方、对象版本、状态、成功通知/查看时间、提醒时间 |
| 匹配 | 候选人+岗位唯一、有效双向兴趣证据、联系方式版本、开放时间 |
| 分享许可 | 谁向该组合分享哪个联系方式版本、告知确认时间与撤销状态 |
| 通知队列 | 业务去重键、发送状态、失败原因、重试时间 |
| 反馈与审计 | 来源、操作者、动作、时间、举报处理；自报结果独立保存 |

兴趣写入、状态复查、唯一匹配创建和通知入队需要事务与数据库唯一约束。按钮绑定对象与版本，服务端检查实际操作者；不能只信客户端角色或按钮参数。

## 10. 衡量实际帮助，不夸大成果

主要观察：合适岗位覆盖率、建档耗时、AI 字段修改率、站内兴趣处理速度、有效双向匹配及联系开放数量。全岗位按城市和类别分组观察，不用全国总量代替局部可用性。

- 官网路径：分别统计合格推荐、申请入口打开、用户自报投递；不能把入口打开计为投递或 Match。
- 入驻路径：分别统计兴趣、24/72 小时处理率、Match、联系开放、通知成功；不能把联系开放计为开聊。
- 24/72 小时处理率采用已具备计时条件且观察窗口完整的兴趣作分母；通知失败另报，不归咎用户。
- 面试和入职反馈可选，不作为继续使用的门槛，也不承诺结果。
- 完全免费；内部观察每个有效推荐/联系的运营成本，不引入付费验证目标。
